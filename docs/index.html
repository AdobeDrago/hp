HP Newsroom · EDS

HP Newsroom and Next-gen AI Pcs on EDS

hp.com's newsroom and AI Solutions pages moved from AEM to Edge Delivery Services, built on the standard aem-block-collection and authored in DA.live — architecture, shared header/footer, GTM, search, blocks, pages and Lighthouse results.

Purpose

  • Rebuild the HP newsroom (home, press releases, press kits, blogs, articles) and the AI Solutions “next-gen-ai-pcs” page on Edge Delivery Services, matched to the live hp.com experience.
  • Provide an authorable header and footer that can also be embedded on external hp.com sites.

Core engineering requirements

  • EDS block-based development (scripts/aem.js + scripts/scripts.js); content authored in DA.live, with Universal Editor models under ue/models/.
  • Header and footer are authored fragments (/nav, /footer); the nav can differ per content folder (Hierarchy Header) and both embed externally with one script (Embedding).
  • GTM click tracking authored through the link-editor Title field or generated by code, loaded after OneTrust consent (GTM).
  • Header search and a search results block backed by HawkSearch and HP Support (Search).
  • Newsroom feeds read the query-index.json index (latest-news, more-articles, press-kits-listing, articles-listing).
  • Related Links are rendered at the CDN edge for SEO (Edge function).
  • A strict CSP is set in head.html.

Hierarchy Header

The header is the header block (blocks/header/header.js). It has no hard-coded links: the whole nav is authored as a fragment in DA and decorated at runtime.

Resolving the nav by content level

The header is resolved by content level, so each content folder can have its own header. The nav metadata says which nav fragment a page loads. It is set for whole folders in the metadata sheet, with a URL pattern in the first column and the nav path in the nav column. The most specific matching pattern wins; pages that match nothing fall back to /nav.

URL patternnavHeader loaded
/**/navGlobal default header
/us-en/**/us-en/navUS English header (newsroom pages)
/us-en/ai-solutions/**/us-en/ai-solutions/navAI Solutions header

To give a section its own header: author a nav fragment in that content folder, then add a row to the metadata sheet with the folder pattern and the fragment path. Every page under the folder picks it up, and a single page can still override it with its own nav page metadata. Only that fragment is fetched, so each section loads just the header features it needs.

Where the content comes from

The fragment path is the nav page metadata, falling back to /nav. It is fetched as <path>.plain.html (prefixed with /content when served from an AEM path) and relative ./media_ images are rebased.

Authoring hierarchy

The fragment is a series of top-level sections. The first four map by position to nav-brand, nav-sections, nav-tools and nav-newsroom. Inside nav-sections the heading levels drive the mega-menu:

Authored asBecomes
H2 with a linkLevel-1 menu item (li.nav-drop + trigger button) with its own flyout panel. An H2 linking to /business-solutions.html is pulled out as the right-hand CTA button instead.
H3 under an H2Heading in the panel's featured column (nav-featured-heading)
UL without imagesPlain link list in the featured column (level 3)
UL containing imagesImage cards column (level 2)

Behaviour

  • Desktop (≥1280px): hover-intent (200 ms) opens/closes panels; click toggles; Escape and outside click close.
  • Below 1280px: hamburger toggles a mobile menu with body scroll lock and an overlay.
  • Tools section: search toggle, cart and account/sign-in flyout (demo sign-in via demo-user.js).
  • Newsroom bar (4th section): shown only when enabled — see the newsroom metadata below. It collapses behind a chevron toggle on small screens.
  • Every nav link gets GTM attributes automatically (header|l1-logo, header|l2-<menu>, header|l3-<menu>); see GTM.

Footer

The footer block loads the fragment named by the footer metadata (default /footer). By position: section 1 = country selector (footer-country), 2 = link columns (accordions on mobile), 3 = legal row incl. the privacy-choices icon.

Embedding header & footer

The header and footer can be dropped into any external page (e.g. other hp.com properties) with one script and two placeholder elements. scripts/global-nav.js renders each into a shadow root, so host-page CSS cannot leak in and HP's CSS cannot leak out.

Snippet

The header and footer are authored once as fragments (/nav, /footer) and served from the published site, so any external site can include them with one script and an empty <header> / <footer>. Content edits publish to every site that embeds them.

<script type="module" src="https://main--hp--adobedrago.aem.live/scripts/global-nav.js"></script> <header></header> <main> ... host page ... </main> <footer></footer>

How it works

  1. The script loads styles/global-nav.css and styles/fonts.css into the host page's head.
  2. A MutationObserver waits for a plain body > header / body > footer (as in the snippet) or an explicit header[data-global-nav], so the script can load before or after the elements.
  3. For each host it attaches the shadow root, loads styles.css, the block CSS (and search-suggest.css for the header) from the code origin, fetches /nav.plain.html or /footer.plain.html, and runs the normal block decorate().
  4. Relative links in the fragment are made absolute against data-link-base (default https://www.hp.com); images are made absolute against the code origin.
Option / eventEffect
data-newsroom="true" (optional attribute on <header>)Show the newsroom bar. Omitted or any other value hides it.
data-link-baseOrigin used to resolve relative nav/footer links.
data-global-navMarks the placeholder; its value becomes loading → loaded or error.
global-nav:loadedBubbling CustomEvent on the host when rendered.
global-nav:errorBubbling event with detail.error; the shadow root falls back to a <slot> so any light-DOM fallback content shows.
Embedded search. When the code origin differs from the page origin, search-utils.js sets isEmbedded: search config (search-client-guid etc.) is read from this site's /nav page metadata instead of the host page, and placeholders.json comes from the code origin.

GTM

GTM click tracking is set up in two ways, and both end up as data-gtm-* attributes that HP's GTM container reads: 1. authored by editors in the DA link editor, and 2. generated by code for the dynamic components, where editors can only override the GTM id through section metadata.

1. Authoring with the link editor

In the link dialog, put the GTM values in the Title field, separated by |. Anything that is not key=value stays as the normal tooltip title.

title = Buy now | category=linkClick | id=hero-cta | value=buy-now | target=_blank
KeyResult
titleThe link's tooltip text (here Buy now). Dropped if identical to the link text.
categorydata-gtm-category — the kind of click, e.g. linkClick
iddata-gtm-id — the placement, e.g. hero-cta
valuedata-gtm-value — the specific link, e.g. buy-now
any other key ([a-z][a-z0-9_-]*)Becomes data-gtm-<key>

This runs through decorateGtmLinks() (scripts/gtm.js) for all of main in decorateMain, and again for the header and footer.

Title format rules

Example: title=Laptops|id=l3-laptops|category=globalNavigation|value=laptops becomes <a title="Laptops" data-gtm-id="l3-laptops" data-gtm-category="globalNavigation" data-gtm-value="laptops"> when the page loads.

  • Pairs can come in any order; use as many as needed.
  • Spaces around | and = are fine, and keys are not case-sensitive.
  • Only the first = splits key from value, so a value may itself contain =.
  • Text without = is a normal title (Shop laptops stays a tooltip and is not tracked). A title that only repeats the link text is removed.
  • Keys must start with a letter and use only lowercase letters, numbers, - or _. Agree new keys and category names with the analytics team.

It works in page content (including buttons and links inside blocks), the header nav fragment and the footer fragment. Related Links are tagged automatically (id=related_links, category=linkClick, value from the link text).

Real example: next-gen-ai-pcs

The AI PCs page is authored entirely with the link-editor method. Spaces around | and = are trimmed, and title= sets the tooltip text.

title=Benefits | id=anchor-nav | category=linkClick | value=benefits-anchor-nav title=Contact Sales | id=anchor-nav | category=contactClick | value=contact-button title=AI at home | id=portfolio-hp-ai-pcs | category=learnClick | value=ai-at-home title=Calculate Your ROI | id=explore-ai-pc-roi-calculator | category=linkClick | value=calculate-roi title=Shop | id=AI-real-world-benefits | category=buyClick | value=shop-button
FieldConvention used on the page
categoryThe kind of click: linkClick (navigation, anchors, video), learnClick (Learn / learn-more), contactClick (Contact Sales), buyClick (Shop / buy)
idThe placement: hero-banner, anchor-nav, portfolio-hp-ai-pcs, meet-fast-intelligent-windows, explore-ai-pc-roi-calculator, hp-iq, most-powerful-windows-security

Links with no key=value in the title, such as the footnote references (tooltip = the disclaimer text), stay plain tooltips and get no GTM attributes. Footnote tracking comes from the code instead (below).

GTM id from section metadata

The dynamic components generate data-gtm-category, data-gtm-id and data-gtm-value themselves (category linkClick, value = article/press-kit slug). The only part an author controls is the id: add a gtm_id row to the Section Metadata block of the section holding the block. The code reads it from the nearest ancestor with data-gtm_id; if it isn't present, the block's default id is used.

BlockDefault GTM id

press-kits-listingkits_link_placement (newsroom_top_hero_banner when placed in the hero); prev/next arrows get prev-arrow / next-arrow

Section Metadata gtm_id | newsroom_hero_cards
  • Type the key as gtm_id, with an underscore.
  • The block removes gtm_id from the page once it has read it, so the id only shows on the card links.
  • One block per section. A second block in the same section won't see the value and falls back to its own default.
  • Authors never type the article value: it is the end of the article URL without .html (e.g. hp-imagine).
  • Every link on a card (image, headline, Read) gets the same three values; press-kits-listing cards are a single link, so one set.

Footnotes (and the dynamic footnote list) are not configurable: their GTM values are generated purely by code, with the value built from the link URL.

Check your work

  1. Preview the page, open DevTools (F12, or Cmd+Option+I), right-click the link → Inspect, and confirm the expected data-gtm-* attributes.
  2. In the Console enable Preserve log, and Cmd/Ctrl-click the link so it opens in a new tab and the page stays put.
  3. On localhost, *.aem.page and *.aem.live GTM loads about 3 seconds after the page with no consent prompt, so you can test there. In production it loads only after the visitor allows Performance & Analytics cookies.

Loading GTM

  • Container IDs come from the gtm-id metadata (normally set once in the site-wide metadata sheet; comma-separated for several containers, e.g. GTM-P9TRBRZ). A page with no gtm-id does not load GTM. scripts/delayed.js loads them ~3 s after load.
  • Consent: the container loads only once OneTrust group 2 (Performance & Analytics) is accepted, hooked through OptanonWrapper. On localhost and *.aem.page/live all groups count as accepted.
  • pb.onOptInGroups entries pushed by HP's tags run their callback when the groups are allowed, and gtm_consent_update is pushed afterwards.

Search

Site search lives in the header, so it is available on every page, including the AI PCs landing page and anywhere the header is embedded. It is powered by HawkSearch (shop and content) plus HP Support (product support), and it hands off to HP's own results page. A separate search block can also render a full results page on this site.

How a search works in the header

  1. Open. The search icon in the nav tools opens the search bar (it is always visible at 1680px and wider). Escape, the close button or a click on the page backdrop closes it.
  2. Type. After 2 characters (250 ms debounce) the header calls HawkSearch autocomplete and HP Support in parallel. Older requests are cancelled when the user keeps typing.
  3. Suggestions panel. A panel opens under the header with:
    • Suggestions — popular search terms with the matching text bolded, plus “See all results”.
    • Shop — up to 3 product cards (name, image, list/sale price) with a total count.
    • Explore — up to 3 articles/content hits with a count.
    • Support — up to 3 HP Support products.
    • If nothing matches: “No results for …”. If HawkSearch fails the panel simply hides.
  4. Choose. Arrow keys move through the options, Enter opens the highlighted one. Each section has a “See all” link.
  5. Submit. Pressing Enter in the box or clicking the search button submits a normal form (GET keyword=) to https://www.hp.com/us-en/shop/sitesearch. Empty searches are ignored.

Results page block

The search block (authored with an optional client-guid row) is a self-contained results page: query box, tabs Shop / Explore / Support, a sort select (Best match, Price low–high, Price high–low, Newest, Top rated — applied to Shop only), result cards and pagination. State is kept in the URL (q, type, page, sort), so a search can be linked, reloaded and navigated with back/forward. Support shows only the top 24 matches with a link to the full support search. Labels come from placeholders.json (e.g. searchPlaceholder, searchSortBy) with English fallbacks.

Article archive — articles-listing Complete

The articles-listing block is the faceted archive over all 1,184 articles. It reads the query index and filters, sorts, and paginates entirely client-side.

Features

  • Card grid — 3-up on desktop; image, title, two-line description, and a Read button.
  • Keyword search across title and description.
  • Media Type facet (type) and a Topics facet over the 46-topic taxonomy.
  • Sort — Newest / Oldest (on created-date) and A–Z / Z–A.
  • Removable chips + Clear all, and a Load More that reveals the next batch of 9.
  • Mobile — single-column cards with a combined Sort & Filter modal, state synced with the desktop controls.

Only real articles appear — a path filter keeps the landing, archive, and any test pages out of the results.

Engineering notes

  • Path normalization: DA source paths use EDS-normalized slugs (lowercase, non-alphanumeric runs → single -, trimmed) — otherwise the preview 404s. ~253 older slugs needed this.
  • Two source templates: a post-2024 template and a pre-2024 one (breakpoint data-src image syntax, DAM paths with spaces) — a recursive walker handles both.
  • Image guards: images ≥ 20 MB and TIFF/GIF/SVG are excluded (some HP DAM mastheads are 48 MB TIFFs / 145 MB+ PNGs).
  • Press kits imported best-effort using existing blocks — galleries collapse into the cards block; interactive download modals and dropdowns were intentionally dropped for this pass; press-specific blocks and variants were added afterwards (see EDS blocks).

Query index Complete

A single query index at /us-en/newsroom/query-index.json is the data source behind every dynamic block on the site — the landing modules and the archive all read from it.

ColumnRole
path, title, description, imageCard rendering
typeMedia Type facet — Press Release (710) / Press Blog (325) / Press Kit (149)
created-dateSort key — ISO YYYY-MM-DD
topicTopics facet — comma-separated slugs
lastModifiedEDS system field — epoch seconds
Mixed date formats. created-date is an ISO string while lastModified is epoch seconds, so every block normalizes both to epoch milliseconds via a toEpoch() helper before sorting or formatting. Blocks sort on the authored created-date — never on lastModified, which resets to migration time.
Managing the index. Add or edit index properties (e.g. the topic column) and rebuild the index from the AEM index-admin tool: tools.aem.live/tools/index-admin (adobedrago/hp).

Topic taxonomy Complete

Article topics aren't in the individual page metadata on hp.com — the newsroom embeds a JSON index of every article and filters it client-side. We extracted that index, mapped each article to HP's fixed 46-topic taxonomy, and backfilled a topic metadata field onto the DA pages that carry topics.

  • 753 pages backfilled with a comma-separated list of topic slugs (e.g. financial, 3d_printing); 416 topicless articles left untouched.
  • The 46-topic list drives the Topics facet in the archive — matched by slug against each article's topic.
  • Backfill inserted a metadata row into each page's existing Metadata block and re-previewed — 753/753 succeeded, 0 failures.

Related links — SEO edge function Complete

On the live site the newsroom "Related links" module is rendered by a third-party BrightEdge integration (the <hp-brightedge-autopilot> component). Its links are written into the page server-side, so search engines and AI crawlers see them in the initial HTML. To preserve that SEO value on Edge Delivery — where blocks normally render client-side — we reproduced the behavior with an AEM Edge Function that stitches the links into the HTML at the CDN edge, with no dependency on BrightEdge source access or a client-supplied API.

What was accomplished

  • Reverse-engineered BrightEdge's IXF link-resolution contract from its public API and the open-source SDK, and reproduced it exactly (verified against every sample newsroom page).
  • Built an AEM Edge Function (aem-edge-functions/) that fetches the page from origin, resolves the correct links for that URL, and injects them above the footer — present in the raw server HTML.
  • Built a matching related-links EDS block (the black bar, collapsible drawer, pipe-separated links) that decorates the injected markup and re-adds the data-gtm-* click-tracking so existing Google Tag Manager analytics keep working unchanged.
  • Covered the resolution logic with 19 unit tests against live BrightEdge fixtures; block passes the project's ESLint + Stylelint.
  • Runs fully on a developer's machine — no custom domain or cloud deployment needed to demo.

How it works

For any /us-en/newsroom page request, the function runs this pipeline at the edge and returns the composed HTML:

// request for /us-en/newsroom(/...) Browser → Edge Function ─┬→ EDS origin (page HTML) └→ api.brightedge.com (link capsule) ↳ inject <div class="related-links"> before </main> → return HTML

Link resolution mirrors BrightEdge's own SDK and resolves in three tiers — this is what makes every newsroom page (landing pages and deep articles) get the right links automatically:

TierSourceUsed by
1 · Page-specificnodes[body_1] in the page's capsuleNewsroom landing pages (newsroom, press-releases, press-kits, blogs)
2 · Page-groupFirst config.page_groups[] rule (by priority) whose regex matches the URL → page_group_nodes[group]Articles — e.g. an AI blog post matches group "AI and Omnibook"; others fall to the "Global Settings" catch-all
3 · Account defaultdefault.jsonFallback when the capsule reports account_id = 0

If anything fails (origin error, capsule error, no links) the function serves the origin HTML unchanged — related links can never break a page.

The BrightEdge contract (reverse-engineered)

StepRule
Normalize + canonicalizeEDS serves extensionless URLs; BrightEdge keys on the live .html URL. Force host to www.hp.com and add .html → e.g. https://www.hp.com/us-en/newsroom.html
Page hashJava 32-bit String.hashCode() of that URL; if negative, return "0" + abs(hash)
FetchGET api.brightedge.com/api/ixf/1.0.0/get_capsule/{account}/{hash} (account f00000000019918, public, no auth)
RenderLink node content is a JSON string → {links:[{url, h1}]}; h1 is the display text (HTML-decoded)

Gotchas (hard-won — read before deploying)

Canonical URL is mandatory. The page hash and the page-group regexes are computed against https://www.hp.com/us-en/…. If you hash the serving host (.aem.page/.aem.live or a staging domain) instead, no capsule and no page-group will match, and every page silently falls through to nothing. Keep CANONICAL_HOST correct per environment.
Extensionless EDS URLs. /us-en/newsroom is a page; /us-en/newsroom.html 404s on EDS. The function adds .html only when computing the BrightEdge key — the actual origin fetch stays extensionless.
An "empty" capsule is not empty. A response with key:"-0" / account_id:0 and blank nodes only means "no page-specific override" — the links come from page-group matching (tiers 2–3). Parsing only the top-level nodes array will wrongly conclude a page has no links.
BrightEdge is cached per-POP. Responses carry x-be-pop and cache-control: max-age=3600; different POPs can transiently differ. Always trust the full capsule (config + page_group_nodes), not a single top-level read, and don't chase phantom "missing" data across regions.
Limits & parity. A program allows only 3 edge functions (dev/staging/prod) — confirm headroom. The data-gtm-value slug is regenerated to match hp.com's convention; spot-check a few labels with the client if exact analytics parity matters.
No committed lockfile. package-lock.json is gitignored, so a fresh clone resolves dependency versions on npm install (fine for the demo, no pinning). If the client wants reproducible installs for the handoff repo, un-ignore it — a one-line change.

Developer notes

Date normalization

Listing blocks share a toEpoch() helper: numeric values below 1e12 are treated as epoch seconds and multiplied by 1000; everything else goes through Date.parse. Sort and display both work off that normalized millisecond value.

Index as the single source

Every dynamic block (latest-news, more-articles, press-kits-listing, articles-listing) defaults to /us-en/newsroom/query-index.json, and an author can override the source with a link in the block. Change the index config once and every feed updates.

Button color gotcha

The project's global button { color: var(--background-color) } renders white — which made block buttons white-on-white. Listing blocks reset this with .articles-listing button { color: inherit }.
