HP · Newsroom Migration

HP Newsroom on Edge Delivery Services

Rebuilding hp.com/us-en/newsroom and the Next-gen AI PCs page on Adobe Edge Delivery Services — migrating the site chrome, importing the full newsroom archive of 1,184 articles into Document Authoring, and building the blocks that power the landing page and the faceted archive.

Project overview

This effort recreates HP's US-English Newsroom — the public home for HP press releases, blogs, and press kits — and the Next-gen AI PCs page on Adobe Edge Delivery Services (EDS), authored through Document Authoring (DA). It follows an EDS block-based development model: the header and footer, articles, landing pages, and archive are all delivered as authorable blocks, with the newsroom feeds driven by a single content query index and the header and footer shared with other HP sites.

Goals

  • Recreate the HP newsroom and the Next-gen AI PCs page on Edge Delivery Services, authored in DA.
  • Migrate the full article archive (press releases, blogs, press kits) with metadata intact.
  • Reproduce the landing pages and a faceted, searchable archive driven by a query index.
  • Match HP's brand identity — typeface, color, header, and footer.
  • Provide a shared global navigation: a header per site section that other HP sites can include.
  • Keep analytics, search and SEO on par with hp.com: GTM click tracking, header search, and Related Links in the initial HTML.

Approach

  • EDS block-based development only — every module is an authorable block, with variants for layout choices.
  • A single content query index (/us-en/newsroom/query-index.json) powers all dynamic listing blocks.
  • Content bulk-imported from the public HP sitemap into DA, one page per article, each carrying an EDS Metadata block.
  • Sort and filter on an authored created-date and a topic taxonomy projected into the index.
  • Authored by the content team: headers per section (metadata sheet), GTM tracking (link editor), and page settings (metadata) need no developer release.
  • Third-party content at the edge: Related Links are rendered by a CDN edge function so they are in the initial page.

Hierarchy Header

The Hierarchy Header lets each part of the website show its own header. Instead of one header for every page, a section of the site — for example the newsroom or AI Solutions — can have a header with the menu items, links and look that suit that audience. Visitors see the header that belongs to the section they are in, and pages stay fast because only that header is loaded.

Why it matters

  • Relevant navigation: AI Solutions visitors see AI Solutions menus, newsroom visitors see the newsroom bar.
  • Managed by the content team: the header is an ordinary document in Document Authoring, so menu changes are made by editors and don't wait for a developer release.
  • One change, many pages: update the header for a section once and every page in that section shows it.
  • Reusable elsewhere: the same header can also appear on other HP websites (see Shared global navigation).

Which header shows where

The website is organised in sections (folders). Each section is linked to the header document it should use. If a section has its own header it uses that; anything not covered uses the main HP header.

Site sectionHeader documentWhat visitors see
Everything else/navThe standard HP header
All US English pages, including the newsroom/us-en/navThe US English HP header; the newsroom pages also show the newsroom bar
AI Solutions pages (e.g. Next-gen AI PCs)/us-en/ai-solutions/navThe AI Solutions header

Setting up a header for a section

  1. Create the header document

    In Document Authoring, create a header page in the section's folder (for example /us-en/ai-solutions/nav) and author its menu.

  2. Point the section at it

    Add a row to the site's settings sheet (the metadata sheet): the section's address pattern (for example /us-en/ai-solutions/**) and the header document in the nav column.

  3. Preview and publish

    Preview a page in the section to confirm the right header appears, then publish the header document and the metadata sheet.

Need a one-off exception for a single page? Set nav in that single page's own metadata and it uses that header instead of its section's.

Good to know

  • Links in the header are tracked for analytics automatically; you don't need to add tracking.
  • Search in the header works on every header, as long as the site's search settings are in place (see Search).
  • Always preview after changing a section's header: if the header document can't be found, the page shows without a header.
Fallback. A page that no section rule covers uses the main header (/nav). A single page can override its section with its own nav page setting.
Managing headers. Add a row to the site's metadata sheet with the section's address pattern and its header document, then preview a page in that section and publish both the header document and the sheet.

Shared global navigation

HP's header and footer are the same global navigation across many HP websites. On Edge Delivery Services that navigation is built once, authored once and shared: the newsroom, the AI Solutions pages and any other HP site can show the same header and footer, and a change made by the content team reaches all of them at the same time. This is how the newsroom keeps hp.com's real navigation without copying it.

The idea

Author once
Header and footer documents in Document Authoring
→
Publish once
Served from the EDS site like any content
→
Show everywhere
Newsroom and any HP site add a small snippet

Why a shared navigation

  • Consistency: visitors see the same menus, search and footer links wherever they are on HP.
  • One place to edit: add a menu item or fix a footer link once; every site that uses the shared navigation updates after publishing.
  • No release on the host site: other teams don't change code or deploy to pick up navigation changes, which saves their time and removes risk.
  • Brand and legal control: the privacy links, country selector and logo stay under one team's control, so every site shows the approved version.

What is shared

PartWhat it includes
HeaderHP logo, mega-menu, search with suggestions, cart, account menu, mobile menu and the optional newsroom bar
FooterCountry selector, link columns and the legal row with the privacy choices icon
BehaviourHover and tap menus, keyboard support, responsive layout, built-in click tracking on every link
Look and feelHP fonts, colours and spacing, applied the same way on every site

Adding it to another HP site

The web team of the host site adds one script and two empty tags once. After that, the content team never has to touch the host site again.

<script type="module" src="https://main--hp--adobedrago.aem.live/scripts/global-nav.js"></script> <header></header> <main> ... host page ... </main> <footer></footer>
  1. Add the script and tags

    Place the script on the page and an empty header and footer tag where the navigation should appear.

  2. The navigation loads itself

    It fetches the current header and footer from the shared site and shows them in place.

  3. Stays up to date

    Every time the content team publishes a change, the host site shows it on the next visit.

GTM

Google Tag Manager (GTM) is how HP's analytics team learns which links and buttons visitors click. On this site tracking is built into the content: editors can tag any link while they write, and the dynamic newsroom components tag themselves. No developer is needed to add or change tracking.

Two ways tracking is added

1. Tagged by the editor2. Tagged automatically
WhereAny link or button in a page, the header or the footerNewsroom cards, header links, accordion, footnotes and Related Links
HowType tracking values into the link's Title fieldNothing to do; the site adds the values itself
Editor can changeEverythingOnly the placement name (the id), through the section settings

1. Tagging a link yourself

When you add or edit a link in Document Authoring, the Edit link dialog has a Title field. Type the tracking values there, separated by a vertical bar ( | ).

title = Buy now | category=linkClick | id=hero-cta | value=buy-now | target=_blank
What you typeWhat it means for analytics
titleThe tooltip visitors see when they hover over the link (here "Buy now").
categoryThe kind of click, for example linkClick (navigation), learnClick (Learn more), contactClick (Contact Sales) or buyClick (Shop).
idWhere on the page the link sits, for example hero-cta or anchor-nav.
valueWhich link it is, in lowercase with hyphens, for example buy-now.
any other nameExtra detail the analytics team asks for, typed the same way, for example position=2.

Tips

  • Use as many pairs as you need, in any order. Spaces around the bars and equals signs are fine.
  • Each pair is written name=value. A title without an equals sign is treated as a normal tooltip and is not tracked.
  • Names must start with a letter and use lowercase letters, numbers, hyphens or underscores. Agree new names and categories with the analytics team so reports stay consistent.
  • It works for links in page content, the header and the footer.

Real example: Next-gen AI PCs

The Next-gen AI PCs page is tagged entirely this way:

title=Benefits | id=anchor-nav | category=linkClick | value=benefits-anchor-nav title=Contact Sales | id=anchor-nav | category=contactClick | value=contact-button title=AI at home | id=portfolio-hp-ai-pcs | category=learnClick | value=ai-at-home title=Calculate Your ROI | id=explore-ai-pc-roi-calculator | category=linkClick | value=calculate-roi title=Shop | id=AI-real-world-benefits | category=buyClick | value=shop-button

When tracking switches on

  • The GTM container is chosen by the gtm-id page setting, normally set once for the whole site in the metadata sheet. A page without it does not load GTM.
  • On the live site, tracking starts only after the visitor accepts Performance & Analytics cookies.
  • On preview and test sites (localhost, .aem.page, .aem.live) it starts about 3 seconds after the page loads, so you can test without the cookie prompt.

Search

Search helps visitors find the right product, article or support page quickly, from any page. It sits in the header, so it is available everywhere the header appears, including the Next-gen AI PCs page and any HP site that uses the shared global navigation. As visitors type, it suggests products, articles and support pages; when they press Enter, it takes them to HP's full search results.

What visitors experience

  1. Open search. Visitors click the search icon in the header. On very wide screens the search box is always visible.
  2. Start typing. After two letters, suggestions appear in a panel under the header.
  3. Pick a suggestion. The panel groups results so visitors can scan quickly:
    • Suggestions — popular searches that match what they typed.
    • Shop — up to three matching products with image and price.
    • Explore — up to three articles and content pages.
    • Support — up to three matching HP support products.
  4. See everything. Each group has a “See all” link, and pressing Enter shows the full results for the search.

Search is also usable with a keyboard, and nothing breaks if a visitor searches for something with no matches: they see a clear “No results” message.

Where visitors end up

Visitor actionWhere they go
Presses Enter, picks a suggestion, or chooses Shop “See all”HP.com search results for products
Chooses Explore “See all”HP.com search results for articles and content
Chooses Support “See all” or a support productThe HP Support site

Search results page

The newsroom can also show a full results page of its own. Visitors get tabs for Shop, Explore and Support, can sort products (best match, price, newest, top rated), and move through pages of results. The address of the page remembers the search, so a results page can be shared, bookmarked, or revisited with the browser's Back button. Editors add it by placing the Search component on a page.

Per-page metadata captured

  • Title ← og:title
  • Description ← meta[description] / og:description, with a fallback to the article's first paragraph (~1/3 of older pages have none)
  • Image ← og:image (absolute DAM URL, sideloaded into the Media Bus on preview)
  • created-date ← HP's created-date meta, normalized to ISO YYYY-MM-DD
  • type — Press Release / Press Blog / Press Kit

Engineering notes

  • Path normalization: DA source paths use EDS-normalized slugs (lowercase, non-alphanumeric runs → single -, trimmed) — otherwise the preview 404s. ~253 older slugs needed this.
  • Two source templates: a post-2024 template and a pre-2024 one (breakpoint data-src image syntax, DAM paths with spaces) — a recursive walker handles both.
  • Image guards: images ≥ 20 MB and TIFF/GIF/SVG are excluded (some HP DAM mastheads are 48 MB TIFFs / 145 MB+ PNGs).
  • Press kits imported best-effort using existing blocks — galleries collapse into the cards block; interactive download modals and dropdowns are intentionally dropped for this pass.

Query index Complete

A single query index at /us-en/newsroom/query-index.json is the data source behind every dynamic block on the site — the landing modules and the archive all read from it.

ColumnRole
path, title, description, imageCard rendering
typeMedia Type facet — Press Release (709) / Press Blog (323) / Press Kit (149)
created-dateSort key — ISO YYYY-MM-DD
topicTopics facet — comma-separated slugs
lastModifiedEDS system field — epoch seconds
Mixed date formats. created-date is an ISO string while lastModified is epoch seconds, so every block normalizes both to epoch milliseconds via a toEpoch() helper before sorting or formatting. Blocks sort on the authored created-date — never on lastModified, which resets to migration time.
Managing the index. Add or edit index properties (e.g. the topic column) and rebuild the index from the AEM index-admin tool: tools.aem.live/tools/index-admin (adobedrago/hp).

Topic taxonomy Complete

Article topics aren't in the individual page metadata on hp.com — the newsroom embeds a JSON index of every article and filters it client-side. We extracted that index, mapped each article to HP's fixed 46-topic taxonomy, and backfilled a topic metadata field onto the DA pages that carry topics.

  • 753 pages backfilled with a comma-separated list of topic slugs (e.g. financial, 3d_printing); 416 topicless articles left untouched.
  • The 46-topic list drives the Topics facet in the archive — matched by slug against each article's topic.
  • Backfill inserted a metadata row into each page's existing Metadata block and re-previewed — 753/753 succeeded, 0 failures.

Related links — SEO edge function Complete

On the live site the newsroom "Related links" module is rendered by a third-party BrightEdge integration (the <hp-brightedge-autopilot> component). Its links are written into the page server-side, so search engines and AI crawlers see them in the initial HTML. To preserve that SEO value on Edge Delivery — where blocks normally render client-side — we reproduced the behavior with an AEM Edge Function that stitches the links into the HTML at the CDN edge, with no dependency on BrightEdge source access or a client-supplied API.

What was accomplished

  • Reverse-engineered BrightEdge's IXF link-resolution contract from its public API and the open-source SDK, and reproduced it exactly (verified against every sample newsroom page).
  • Built an AEM Edge Function (aem-edge-functions/) that fetches the page from origin, resolves the correct links for that URL, and injects them above the footer — present in the raw server HTML.
  • Built a matching related-links EDS block (the black bar, collapsible drawer, pipe-separated links) that decorates the injected markup and re-adds the data-gtm-* click-tracking so existing Google Tag Manager analytics keep working unchanged.
  • Covered the resolution logic with 19 unit tests against live BrightEdge fixtures; block passes the project's ESLint + Stylelint.
  • Runs fully on a developer's machine — no custom domain or cloud deployment needed to demo.

How it works

For any /us-en/newsroom page request, the function runs this pipeline at the edge and returns the composed HTML:

// request for /us-en/newsroom(/...) Browser → Edge Function ─┬→ EDS origin (page HTML) └→ api.brightedge.com (link capsule) ↳ inject <div class="related-links"> before </main> → return HTML

Link resolution mirrors BrightEdge's own SDK and resolves in three tiers — this is what makes every newsroom page (landing pages and deep articles) get the right links automatically:

TierSourceUsed by
1 · Page-specificnodes[body_1] in the page's capsuleNewsroom landing pages (newsroom, press-releases, press-kits, blogs)
2 · Page-groupFirst config.page_groups[] rule (by priority) whose regex matches the URL → page_group_nodes[group]Articles — e.g. an AI blog post matches group "AI and Omnibook"; others fall to the "Global Settings" catch-all
3 · Account defaultdefault.jsonFallback when the capsule reports account_id = 0

If anything fails (origin error, capsule error, no links) the function serves the origin HTML unchanged — related links can never break a page.

The BrightEdge contract (reverse-engineered)

StepRule
Normalize + canonicalizeEDS serves extensionless URLs; BrightEdge keys on the live .html URL. Force host to www.hp.com and add .html → e.g. https://www.hp.com/us-en/newsroom.html
Page hashJava 32-bit String.hashCode() of that URL; if negative, return "0" + abs(hash)
FetchGET api.brightedge.com/api/ixf/1.0.0/get_capsule/{account}/{hash} (account f00000000019918, public, no auth)
RenderLink node content is a JSON string → {links:[{url, h1}]}; h1 is the display text (HTML-decoded)

Gotchas (hard-won — read before deploying)

Canonical URL is mandatory. The page hash and the page-group regexes are computed against https://www.hp.com/us-en/…. If you hash the serving host (.aem.page/.aem.live or a staging domain) instead, no capsule and no page-group will match, and every page silently falls through to nothing. Keep CANONICAL_HOST correct per environment.
Extensionless EDS URLs. /us-en/newsroom is a page; /us-en/newsroom.html 404s on EDS. The function adds .html only when computing the BrightEdge key — the actual origin fetch stays extensionless.
An "empty" capsule is not empty. A response with key:"-0" / account_id:0 and blank nodes only means "no page-specific override" — the links come from page-group matching (tiers 2–3). Parsing only the top-level nodes array will wrongly conclude a page has no links.
BrightEdge is cached per-POP. Responses carry x-be-pop and cache-control: max-age=3600; different POPs can transiently differ. Always trust the full capsule (config + page_group_nodes), not a single top-level read, and don't chase phantom "missing" data across regions.
Limits & parity. A program allows only 3 edge functions (dev/staging/prod) — confirm headroom. The data-gtm-value slug is regenerated to match hp.com's convention; spot-check a few labels with the client if exact analytics parity matters.
No committed lockfile. package-lock.json is gitignored, so a fresh clone resolves dependency versions on npm install (fine for the demo, no pinning). If the client wants reproducible installs for the handoff repo, un-ignore it — a one-line change.

Known limitations & accepted quirks Review

Accepted for this delivery — each is a candidate for follow-up if Code & Theory needs it resolved for production.

  • Article pages are at MVP fidelity, not a production pixel match
    Individual article pages were migrated and assembled using existing blocks to reach an MVP — they don't yet replicate the exact styling of the production newsroom. Example: a migrated 2026 press release. Matching production styling per template is a follow-up for Code & Theory.
  • created-date clustering (~87%)
    1,027 of 1,181 articles show 2024-06-18 because HP's 2024 CMS migration reset the date on older content. True editorial dates are recoverable from the embedded newsroom JSON (ad, epoch ms) but were not applied this pass.
  • Missing descriptions (~1/3 of older pages)
    Handled with a fallback to the article's first paragraph; index shows 1,165 of 1,181 with a description.
  • Press-kit page interactivity dropped
    The press-kit articles' overall page interactivity was not migrated — download modals, dropdowns, and interactive asset galleries; galleries were flattened into the cards block. Faithful, fully interactive press-kit pages are a separate scope.
  • Oversized / unsupported images excluded
    Images ≥ 20 MB and TIFF/GIF/SVG are skipped (some HP DAM mastheads are 48 MB TIFFs or 145 MB+ PNGs). Affected heroes fall back to no masthead.
  • 416 articles have no topic
    Source data has no topic for those articles, so they won't match any Topics facet until tagged.
  • Topic data provenance
    The topic taxonomy was scraped from HP's public embedded JSON. Confirm this source is acceptable for production use before go-live.

Developer notes

Date normalization

Listing blocks share a toEpoch() helper: numeric values below 1e12 are treated as epoch seconds and multiplied by 1000; everything else goes through Date.parse. Sort and display both work off that normalized millisecond value.

Index as the single source

Every dynamic block (latest-news, more-articles, press-kits-listing, articles-listing) defaults to /us-en/newsroom/query-index.json, and an author can override the source with a link in the block. Change the index config once and every feed updates.

Button color gotcha

The project's global button { color: var(--background-color) } renders white — which made block buttons white-on-white. Listing blocks reset this with .articles-listing button { color: inherit }.
